# AGENTS.md

## Repo Shape
- This is an Argo CD GitOps repo for a k3s homelab; there are no package scripts, app tests, or language build steps at the root.
- Argo CD tracks `main` from `https://github.com/kacperjarocki/homelab.git`. The root Application (`argocd/bootstrap/root.yaml`) syncs `argocd/root/` recursively; everything else is reached from there.
- `argocd/root/` holds only Argo CD objects (`Application`, `AppProject`). Component configuration lives in `infra/` (platform) and `apps/` (workloads).

## Layout
- `argocd/root/projects/`: AppProjects `infra`, `apps` and `pi-agents`. `sourceRepos` is an explicit allow-list; a new Helm repo must be added there or the Application is rejected.
- `argocd/root/apps/pi-agents-root.yaml` is a nested app-of-apps that syncs `k8s/argocd/` from the separate `KacperJarocki/pi-agents` repo; its child Applications use project `pi-agents`, whose `destinations` list the namespaces that repo may touch (`argocd`, `iot-security`, `iot-security-dev`, `cnpg-system`, `strimzi-system`).
- `argocd/root/infra/*.yaml` and `argocd/root/apps/*.yaml`: one Application per component, named after its Helm release.
- `infra/<component>/values.yaml` and `apps/<ns>/<app>/values.yaml`: Helm values, referenced from the Application as `$values/<path>`.
- Extra plain manifests sit next to the values in `manifests/` (or `issuers/`, `config/`, `policies/`) and are the `path` of the Git source. A directory with a `kustomization.yaml` is rendered with kustomize, otherwise every YAML file is applied as-is.
- `network/opnsense/`: OpenTofu for the OPNsense firewall (not an Argo CD app); see its README.md. Applied by `.github/workflows/opnsense.yml` on the in-cluster ARC runner `homelab-arm64`.
- Adding a component means: values/manifests dir + Application file + sync wave; nothing has to be registered in a central kustomization.

## Validation Commands
- `scripts/validate-local.sh` renders every Application like Argo CD would (`helm template` with the referenced values, `kubectl kustomize`, YAML parse). Needs `helm`, `kubectl`, `yq` and network access for charts. Git sources that point at other repositories are skipped.
- Single chart: `helm template <release> <chart> --repo <url> --version <ver> -n <ns> -f <values.yaml> > /dev/null`.
- Plain manifests against a reachable cluster without changing it: `kubectl apply --dry-run=server -f infra/<component>/manifests`.
- With Argo CD installed: `argocd app diff <name>` shows live vs Git for one app; `kubectl -n argocd get applications` shows sync/health state for all.

## Ordering and Sync
- Dependencies are expressed with `argocd.argoproj.io/sync-wave` on the Application files in `argocd/root/`, never by file order. Current waves: projects (-10) -> cert-manager, metallb, kyverno, external-secrets (0) -> issuers, metallb-config, kyverno-policies (1) -> traefik, longhorn, argocd, kured, arc (2) -> rustfs, arc-runners, monitoring stack, falco (3) -> pi-agents-root, opnsense-ops (4).
- The root app only advances to the next wave once every Application of the current wave is Healthy. A stuck child app blocks later waves from being created on a fresh cluster; already-created apps keep syncing independently.
- Every Application has `ServerSideApply=true` (large CRDs), `CreateNamespace=true`, automated prune + selfHeal and a `resources-finalizer` (removing the file from Git deletes the resources). The root app intentionally has no finalizer.
- Applications that apply custom resources of CRDs installed by another Application carry `SkipDryRunOnMissingResource=true`.
- Namespaces are created by Argo CD; Pod Security labels are declared via `syncPolicy.managedNamespaceMetadata` on the Application that owns the namespace (metallb for `networking`, longhorn for `longhorn-system`).

## Argo CD Itself
- Installed from the `argo-cd` Helm chart with `infra/argocd/values.yaml`; after bootstrap the `argocd` Application manages it (self-management). Keep the chart version in `argocd/root/infra/argocd.yaml`; `scripts/bootstrap-argocd.sh` reads it from there.
- `infra/argocd/values.yaml` restores the `argoproj.io/Application` health check (required for sync waves), sets annotation-based resource tracking, and ignores webhook `caBundle` diffs. Do not remove those.
- Kyverno policies under `infra/kyverno/policies/` must keep excluding the `argocd` namespace, otherwise Argo CD pods (no resource limits) are rejected.

## Repo-Specific Gotchas
- Renovate uses its `argocd` manager on `argocd/root/**/*.yaml`; chart versions must stay as `targetRevision` next to `chart:` for it to work.
- GitVersion releases run only on pushes to `main`; version bumps are driven by Conventional Commit prefixes in `GitVersion.yml` and tags are pushed as `v<MajorMinorPatch>`.
- Some manifests contain secret references, and at least one values file contains plaintext credentials; avoid pasting full rendered YAML into responses unless necessary.
- Certificates and ingresses use the `homelab.kacperjarocki.dev` / `kacperjarocki.dev` DNS zone and cert-manager ClusterIssuers defined under `infra/cert-manager/issuers/`.
- Loki values set `test.enabled: false`; chart >= 7.5.0 refuses to render otherwise when the canary is disabled.
- Loki stores chunks in the in-cluster RustFS (`infra/rustfs`, chart from charts.rustfs.com; MinIO is not an option any more, its public images were withdrawn). Loki's S3 credentials are `${S3_ACCESS_KEY_ID}`/`${S3_SECRET_ACCESS_KEY}` expanded from the `loki-s3` Secret (`-config.expand-env=true`); RustFS reads `rustfs-credentials` (`RUSTFS_ACCESS_KEY`/`RUSTFS_SECRET_KEY`). Both are created by `scripts/create-object-storage-secrets.sh`, never committed. Buckets are created by the `rustfs-buckets` Job, an Argo CD PostSync hook in `infra/rustfs/manifests/`. Hooks are not part of the diff, so adding a bucket to `BUCKETS` does not make `rustfs` OutOfSync and nothing runs: sync the `rustfs` Application by hand afterwards (Argo CD UI, or `kubectl -n argocd patch application rustfs --type merge -p '{"operation":{"sync":{"revision":"main"}}}'`).
- Alerting: rules in `apps/monitoring/kube-prometheus-stack/manifests/alert-rules.yaml` (own set; the chart's default rules stay off), Alertmanager -> self-hosted ntfy (`apps/monitoring/ntfy`, LAN only, `auth-default-access: deny-all`). Users and tokens live in the `ntfy-auth` and `alertmanager-ntfy` Secrets created by `scripts/create-alerting-secrets.sh` (prints the phone login; never committed). ntfy refuses to start if an `auth-access` entry names a user missing from the Secret. Each rule has a `topic` label (workloads, nodes, storage, network, monitoring); Alertmanager routes it to the ntfy topic `homelab-<topic>`, every `severity=critical` alert to `homelab-critical` instead, and anything without a topic to `homelab-alerts`. A new topic needs a route + receiver in the kube-prometheus-stack values (the ntfy ACL `homelab-*` already covers it). Check new rule expressions against the live Prometheus before committing: an expr that matches today fires on sync. Notifications are rendered by the custom ntfy template `homelab.yml` (in the ntfy ConfigMap, mounted under `templates/`) from each rule's `title`/`summary`/`description` annotations; node-exporter rules join `node_uname_info` so alerts name the host (`node`) instead of `<ip>:9100`. Grafana shows the same alerts in the `Homelab / Alerts` dashboard (`manifests/dashboard-alerts.yaml`, built on `ALERTS`) and under Alerting > Alert rules (Prometheus datasource `manageAlerts`). Node rules filter `group!="firewall"`: Alloy writes the OPNsense node-exporter under the same metric names.
- Helm charts from OCI registries (ARC from `ghcr.io/actions/actions-runner-controller-charts`) use `repoURL` without `oci://` plus `chart:`; that exact string must be in the AppProject `sourceRepos`, and `validate-local.sh` renders such sources as `oci://<repoURL>/<chart>`.
- Self-hosted runners (ARC): controller `arc` in `arc-systems` (release name fixes the ServiceAccount `arc-gha-rs-controller`), scale set `homelab-arm64` in `arc-runners` (`infra/arc-runners`, repo-level, max 1 runner, PSA restricted, egress-only NetworkPolicy: DNS, RustFS, `10.20.0.1:443`, public HTTPS). `controllerServiceAccount` must stay set explicitly (Helm `lookup` does not run under Argo CD), and `flags.watchSingleNamespace` must stay unset (it would put a Role into the wave-3 namespace from a wave-2 app). The repo is public: no workflow job with `runs-on: homelab-arm64` may run on `pull_request`/`pull_request_target`. Secrets `arc-github-app` and `opnsense-tofu` come from `scripts/create-network-iac-secrets.sh`, never committed.
- OPNsense ops in the cluster: `infra/opnsense-ops` (namespace `opnsense`, Secret `opnsense-api`) saves `config.xml` daily to `s3://tofu-state/backups/daily/` and checks interface assignments/addresses/bridge hourly against `interfaces-expected.json` (no write API exists for them; a failed run fires `OPNsenseInterfaceDrift`, excluded from `JobFailed`); firewall syslog (filter log, Suricata EVE) arrives via the `alloy-syslog` LoadBalancer `10.20.30.51:514/udp` into `loki.source.syslog "opnsense"`, label `job="opnsense/syslog"`. There is no opnsense-exporter; OPNsense metrics come only from its node_exporter.
- OpenTofu state for `network/opnsense` is in RustFS bucket `tofu-state` (S3 backend, endpoint from `AWS_ENDPOINT_URL_S3`), always encrypted (state and plan, `enforced`) with `TF_VAR_state_passphrase`. Applies back up `config.xml` to `s3://tofu-state/backups/` first.
- Grafana admin login comes from the `grafana-admin` Secret (`scripts/create-grafana-admin-secret.sh`, which also resets the password in Grafana's database). Do not drop `grafana.admin.existingSecret`: the chart would generate a new random password on every Argo CD render (its Helm `lookup` does not run under Argo CD) that never matches the database.
- Runtime threat detection: Falco (`infra/falco`, namespace `falco`, PSA privileged) runs as a DaemonSet with the `modern_ebpf` driver (all nodes have BTF) and the CRI socket `/run/k3s/containerd/containerd.sock`. Events are JSON on stdout, so Alloy ships them to Loki (`{namespace="falco", container="falco"} | json`); Falcosidekick only exists for its `/metrics` (`falcosecurity_falcosidekick_falco_events_total`, labels `rule`, `priority_raw`, `k8s_ns_name`, `k8s_pod_name`, `hostname`), which feed `FalcoCriticalEvent`/`FalcoWarningEvent` (group `security`, topic `security`). Don't enable Falcosidekick's Loki output, it would store each event twice. Benign detections are silenced with exceptions in `customRules` of the values, never by raising `priority`. The Falcosidekick ServiceMonitor only renders when the cluster has the monitoring CRDs, so a local `helm template` without `--api-versions` does not show it.
- Node OS reboots go through kured (`infra/kured`, namespace `kube-system`): one node at a time, drained, 02:00-05:00 Europe/Warsaw, held while any alert fires except `NodeRebooted` and the Falco detections (`alertFilterRegexp`). It only works if `Unattended-Upgrade::Automatic-Reboot` is `false` on the nodes; with it on, unattended-upgrades reboots each node itself right after a glibc/kernel update, undrained.
